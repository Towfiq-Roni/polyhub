## Objective

A SUPER_ADMIN can create, list, view, edit, activate, deactivate users and reset a user's password (admin-set, no email) through `/api/v1/users`, with argon2id hashes never exposed, sessions revoked on deactivate/reset, and the last-active-SUPER_ADMIN deactivation rejected 422. Afterwards a deactivated user cannot log in, refresh, or use an access token.

## Design decisions (implementer follows verbatim)

**D1 (a) Interim authorization.** `PermissionsGuard` (#4) and catalog (#3) do not exist. Rule 7 forbids ad hoc permission strings, so #2 uses NO permission strings: class-level `@UseGuards(JwtAccessGuard, SuperAdminGuard)`. `SuperAdminGuard` loads `request.user.id`, checks `prisma.userRole.findFirst({ where: { userId, role: { name: ROLE_NAMES.SUPER_ADMIN, status: 'ACTIVE' } } })`, else `ForbiddenException('Forbidden')` (403). `ROLE_NAMES` already lives in `@hub/shared`. Mark file `// ponytail: interim SUPER_ADMIN-only gate (SRS FR-ADMIN-02 is admin-only) → #4 replaces with @RequirePermissions(...) from the packages/shared catalog; delete this guard then`. Recommended keys for #3 to define (NOT added now): `users.view`, `users.create`, `users.update`, `users.deactivate`, `users.reset_password`.

**D2 (b) Rule 9 inside #2 (minimal).** Shipping a deactivate endpoint that can violate non-negotiable rule 9 is unacceptable, so #2 enforces last-active-SUPER_ADMIN on **deactivate only**, in the service (422 `UnprocessableEntityException('Cannot deactivate the last active Super Admin')`). #5 (F-30) still owns: role-removal path (UserRole removal / role deactivation, which need #3/#4), extracting the check into a shared invariant service, and exhaustive F-30-tagged tests. Race-safe: inside the `$transaction`, first `SELECT u.id FROM users u JOIN user_roles ur ON ur.user_id=u.id JOIN roles r ON r.id=ur.role_id WHERE u.status='ACTIVE' AND r.status='ACTIVE' AND r.name=${ROLE_NAMES.SUPER_ADMIN} FOR UPDATE OF u` (tagged `$queryRaw`, parameterized); if the target id is in the result and result length is 1, throw 422 before any write. Concurrent mutual deactivations serialize on the row locks (READ COMMITTED re-evaluates the WHERE after the first commit).

**D3 (c) Audit interim.** `AuditLog` is #6. #2 emits a structured Nest `Logger('Audit')` JSON line per sensitive write: `{ actorId, action, entityType:'User', entityId, before, after }` with `before/after` limited to `{ email, name, status }` (null when n/a). Actions: `user.create | user.update | user.deactivate | user.activate | user.reset_password`. Emitted AFTER the transaction commits, via ONE private method `audit(...)` in the service. Never include `password`, `passwordHash`. `// ponytail: logger line, no AuditLog table yet → #6 replaces this method body with the AuditLog write (and #6 must cover users routes)`. Orchestrator: log in DECISIONS.md that rule 8 for users is interim until #6.

**D4 (d) Admin-mediated reset.** `POST /users/:id/reset-password` body `{ password }` — the admin SETS the temp password (SRS "admin-set temp password"), communicated out of band; no generation, no echo, no SMTP. Hash with `hashPassword` imported from `../auth/auth.service` (argon2id; do not re-implement). In ONE `$transaction`: `user.update({ passwordHash, failedLoginAttempts:0, firstFailedAttemptAt:null, lockoutUntil:null })` (admin reset also unlocks) + `session.updateMany({ where:{ userId, revokedAt:null }, data:{ revokedAt: new Date() } })`. Create-user takes the same `password` field. Password policy (assumption, no SRS policy): `@IsString() @MinLength(12) @MaxLength(128)`. Accepted tradeoff (ADR-0004): already-issued access JWTs stay valid ≤1 day after RESET (stateless); after DEACTIVATE they die immediately because `JwtAccessStrategy` re-checks `status==='ACTIVE'` per request. No forced-change-on-first-login (no ERD field, no self-service change-password endpoint exists) — out of scope.

**D5 Deactivate/activate.** `POST /users/:id/deactivate` (200): `$transaction` = D2 lock+check, `user.update({status:'INACTIVE'})`, `session.updateMany(revoke all active)`. Already INACTIVE → 200 idempotent no-op (no writes, no audit). `POST /users/:id/activate` (200): `status:'ACTIVE'` + clear lockout fields; already ACTIVE → idempotent no-op. No `DELETE` route anywhere (ERD §1.4: archive via status).

**D6 Inactive-login hole fix (required).** `AuthService.login` currently has NO status check, so a deactivated user would receive tokens. Change `if (!user)` to `if (!user || user.status !== 'ACTIVE')` → same generic 401 `Invalid credentials` (auth spec Design Decision #4). This is the only auth edit.

**D7 Shapes.** Request DTOs (class-validator, global ValidationPipe whitelist; whitelist silently strips unknown keys): Create `{ email @IsEmail (trim+lowercase via @Transform), name @IsString @IsNotEmpty @MaxLength(120) trimmed, password }`; Update `{ email?, name? }` (both `@IsOptional`; service throws 400 `BadRequestException('At least one field required')` if neither present — so `PATCH {status:'INACTIVE'}` or `{password:'x'}` is a 400, never a status/password change); ResetPassword `{ password }`. Response `UserAdminViewDto`: `id, email, name, status, roles: string[] (role names), lastLoginAt: Date|null, createdAt, updatedAt`. Build it from an explicit Prisma `select` (never load/serialize `passwordHash`, `failedLoginAttempts`, `firstFailedAttemptAt`, `lockoutUntil`). Envelope `{ data }` via the existing interceptor. List returns all users ordered `createdAt asc` — no pagination (`// ponytail: ≤5 users (NFR-SCALE-01) → add ?page&limit&q when user count grows`). Id params use `ParseUUIDPipe` (400 on malformed).
Errors: duplicate email (create/update) → 409 `Email already in use` (catch Prisma `P2002`); unknown id → 404 `User not found` (use `findUnique`; for update/reset/etc. read first, which also gives the audit `before`).
Email stored lowercase, so case-variant duplicates are impossible. Known gap (NOT fixed here): `login` looks up email exactly, so a mixed-case login attempt against a lowercased account 401s — Open Question Q3.

**D8 (f) Schema.** NO schema change, NO migration (User/Role/UserRole/Session suffice). Gate S6 proves it. If implementer thinks one is needed: stop, report.

**D9 (e) Roles on users.** Create does NOT accept roles; no role-assignment endpoint in #2 (belongs to #3/#4/#5 role work). `roles` in the view is read-only. A newly created user has zero roles = zero permissions.
