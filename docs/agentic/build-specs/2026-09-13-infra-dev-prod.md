# Build Spec — TASKS.md #41 + #42: Dev + Prod Infra (multi-level docker-compose + Makefile)

Date: 2026-09-13 · Planner: hub-planner · Skills loaded: `hub-deploy` · Authoritative sources read: `analysis/deployment-plan.md` (full), `analysis/task-breakdown.md` Phase 1, `CLAUDE.md` (Locked Stack, Non-Negotiable Rules, Delegation Rules, Guardrails), `docs/memory/DECISIONS.md` DEC-081, `.claude/skills/hub-deploy/SKILL.md`, live repo state (`apps/api` source, `package.json`, `.gitignore`, `apps/api/.env(.example)`).

## 1. Objective

Give the repo real infra scaffolding instead of the ad-hoc `docker run` this session hand-rolled: a multi-level Docker Compose setup (`infra/docker-compose.yml` base + `.dev.yml`/`.prod.yml` overlays) driven through a root `Makefile`, a multi-stage `apps/api` Dockerfile, an nginx routing config, and the release-time `deploy.sh`/`smoke.sh` scripts — everything buildable and locally verifiable today, with `apps/web`'s Dockerfile/nginx route and the actual GitHub Actions workflows and Oracle VM explicitly left as later, separately-scoped work (TASKS.md #40/#43/#44).

## 2. Ground truth this spec relies on

- `analysis/deployment-plan.md` §0 topology: nginx is the only public entrypoint (`80/443`); `web`, `api`, `postgres` sit behind it on an internal network; `pg-backup` cron does nightly dumps → B2.
- §5 service contract table: nginx routes `/`→web, `/api`→api, `/files/` `internal;` only, `client_max_body_size 25m`; api runs `prisma migrate deploy` as a **separate deploy step**, never on boot; postgres tuned `shared_buffers=256MB`.
- §6 deploy pipeline: `pull` → `docker compose run --rm api npx prisma migrate deploy` → `up -d` → `./scripts/smoke.sh` (health + login-page 200) → rollback to `LAST_TAG` on failure.
- §9 hardening: nginx `limit_req` on `/api/v1/auth/login` (5 r/min burst 5) and general API (30 r/s); HSTS/X-Content-Type-Options/X-Frame-Options DENY/Referrer-Policy; files strictly behind RBAC + `internal` nginx location.
- `hub-deploy` skill: <500MB steady-state RAM guidance, arm64-primary/amd64-fallback multi-arch, only nginx exposes ports, secrets only via GitHub Environment→VM `.env` at deploy time, migrations forward-only/explicit-step, base images rebuilt weekly (separate CI concern, #43).
- Live repo facts used to avoid inventing anything: `apps/api` already boots via `ConfigService.getOrThrow`, requires `DATABASE_URL`/`JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET`/`SUPER_ADMIN_EMAIL`/`SUPER_ADMIN_PASSWORD`/`WEB_ORIGIN`/`PORT` (see `apps/api/src/config/env.validation.ts`), exposes `GET /api/v1/health` (`apps/api/src/health/health.controller.ts`, globalPrefix `api/v1` set in `main.ts`) and trusts the first proxy hop already (`app.getHttpAdapter().getInstance().set('trust proxy', 1)`), and `apps/api/.env`/`.env.example` already exist and are gitignored. `apps/web` does not exist (TASKS.md #40).

## 3. Design decisions this spec locks in (read before building — do not re-derive differently)

1. **Base compose has no standalone top-level `volumes:`.** `infra/docker-compose.yml` is never invoked alone (always `-f base -f overlay`); each overlay (`dev`/`prod`) declares and binds its own named Postgres volume (`pgdata_dev` / `pgdata_prod`) so dev and prod data can never collide on the same host. Compose merge rules replace a service's `volumes:` mount-target entry when an overlay targets the same container path, so this works cleanly.
2. **`web` is deliberately absent from `infra/docker-compose.prod.yml`.** Do not invent a placeholder Next.js app or a `web` service stub. Add a `# TODO(TASKS.md #40)` comment at the exact spot it will go. nginx's `/` location returns a real HTTP 503 with a body explaining why, plus a commented `proxy_pass http://web:3000;` line for later.
3. **Reconciling deployment-plan §5's "single `docker-compose.prod.yml` on the VM" with the stakeholder's multi-level-compose requirement**: on the VM, both `infra/docker-compose.yml` (base) and `infra/docker-compose.prod.yml` (overlay) get staged into `/opt/hub/` (by the CI workflow, TASKS.md #43, out of scope here) and `deploy.sh` always invokes them together with `-f docker-compose.yml -f docker-compose.prod.yml`. This is a deliberate reconciliation, not a silent deviation — flag it as such if questioned.
4. **RAM budget tension, resolved explicitly**: `analysis/deployment-plan.md` §5 prescribes `shared_buffers=256MB` for postgres by name; `hub-deploy`'s skill guidance is an informal <500MB *total* steady-state target. `mem_limit` values below (postgres 320m / api 180m / nginx 32m = 532m) run ~6% over that soft target with `web` not even running yet. Resolution: honor the authoritative deployment-plan tuning value as-is (CLAUDE.md precedence: financial/deploy-runbook specifics outrank the skill's soft heuristic); do not silently shrink `shared_buffers` to hit 500MB. Note this as a known, accepted number — not something to "fix" quietly — and revisit once `apps/web`'s real footprint is measured.
5. **File uploads volume (`resources_data`)** is wired now (api read-write mount, nginx read-only mount + `internal /files/` alias) even though no upload feature exists yet, because `analysis/deployment-plan.md` §5's VM directory layout already specifies `data/resources/` as part of the topology — this is config-only forward-wiring of an already-spec'd path, not new application logic.
6. **No CI workflow YAML, no real VM/DNS/TLS/B2 credentials, no `apps/web` Dockerfile** — those are TASKS.md #40/#43/#44. `infra/scripts/deploy.sh` and `infra/scripts/smoke.sh` ARE in scope (hub-deploy's file-ownership table: "Release logic → `infra/scripts/deploy.sh`"), even though the workflow that invokes them is not.

## 4. Batches (build in this order; ≤3 files each)

### Batch 1 — Dev compose core (3 files, new)

1. **`infra/docker-compose.yml`** (new) — base file. One service, `postgres` (`postgres:16-alpine`), env vars `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` (no defaults — supplied by whichever `--env-file` the overlay uses), a `pg_isready` healthcheck, attached to a `hub-net` bridge network. No `ports:`, no `volumes:`, no `restart:` — those are overlay concerns.
2. **`infra/docker-compose.dev.yml`** (new) — dev overlay. Adds to `postgres`: `ports: ["${POSTGRES_PORT:-5432}:5432"]` (dev is the one place Postgres is host-reachable — for `psql`/GUI tools — since `apps/api` runs on the host via `pnpm dev`, not in Compose) and `volumes: [pgdata_dev:/var/lib/postgresql/data]`; declares top-level `volumes: pgdata_dev:`.
3. **`infra/.env.dev.example`** (new) — documents `POSTGRES_USER=hub`, `POSTGRES_PASSWORD=hub_dev_local_only`, `POSTGRES_DB=hub_dev`, `POSTGRES_PORT=5432`, plus a comment showing the exact `DATABASE_URL` value `apps/api/.env` must use to match (`postgresql://hub:hub_dev_local_only@localhost:5432/hub_dev`). Real values are fine here (local-only, never internet-reachable) — this is the one `.env*.example` file allowed non-blank secrets, and only because they're throwaway local-dev-only values.

Why this order: nothing else depends on anything but this batch; it alone already satisfies TASKS.md #41 end to end.

### Batch 2 — Wire Makefile (dev) + gitignore + local env convention (3 files: 1 new, 2 edited)

1. **`Makefile`** (new, repo root) — `.PHONY: dev-up dev-down dev-logs dev-psql`, a `COMPOSE_DEV` variable (`docker compose -p hub-dev -f infra/docker-compose.yml -f infra/docker-compose.dev.yml --env-file infra/.env.dev`), and targets:
   - `dev-up`: `$(COMPOSE_DEV) up -d` + an echoed reminder to point `apps/api/.env`'s `DATABASE_URL` at the dev container.
   - `dev-down`: `$(COMPOSE_DEV) down`
   - `dev-logs`: `$(COMPOSE_DEV) logs -f`
   - `dev-psql`: `$(COMPOSE_DEV) exec postgres psql -U hub -d hub_dev` (hardcoded to match `.env.dev.example` defaults — simplest working thing, no shell-var plumbing needed for a single-command convenience target).
   Leave a comment block noting prod targets land in a later batch (Batch 6) — do not stub empty prod targets now.
2. **`.gitignore`** (edit) — under the existing `# secrets & env` section, add `infra/.env.dev`, `infra/.env.prod`, `infra/.env` (the rendered/real files) — `*.example` files stay tracked, nothing else in this section changes.
3. **`apps/api/.env`** (edit, gitignored/local file — read its current `DATABASE_URL` value first) — set `DATABASE_URL=postgresql://hub:hub_dev_local_only@localhost:5432/hub_dev` to match Batch 1's `.env.dev.example` convention, replacing whatever ad-hoc value is there now. This is the one and only `apps/api` touch in the whole spec, and it's config data, not code.

### Batch 3 — `apps/api` Dockerfile (2 files, new)

1. **`apps/api/Dockerfile`** (new) — multi-stage, **build context is the repo root** (this is load-bearing: it's a pnpm workspace, `apps/api` alone can't `pnpm install`). Stages:
   - `base`: `FROM node:20-alpine`, `RUN corepack enable`, `WORKDIR /repo`.
   - `deps` (from `base`): copy `pnpm-workspace.yaml pnpm-lock.yaml package.json`, `apps/api/package.json`, `packages/shared/package.json`, then `RUN pnpm install --frozen-lockfile`.
   - `build` (from `deps`): `COPY . .`, `RUN pnpm --filter @hub/api... run build` (the `...` suffix pulls in `packages/shared` as a build dependency), `RUN pnpm --filter @hub/api exec prisma generate`.
   - `runtime` (from `base`): `ENV NODE_ENV=production`; copy `package.json`/`pnpm-workspace.yaml`/`pnpm-lock.yaml`/`apps/api/package.json`/`packages/shared` from `build`; `RUN pnpm install --frozen-lockfile --prod --filter @hub/api...`; **then** (order matters — after install, so nothing gets overwritten) `COPY --from=build` the compiled `apps/api/dist`, `apps/api/prisma` (schema, needed at runtime by the Prisma client), and the generated `apps/api/node_modules/.prisma`; `WORKDIR /repo/apps/api`; `USER node` (non-root, uses the `node` user baked into the official image — no new user creation needed); `HEALTHCHECK` via `wget -q -O- http://localhost:${PORT:-4000}/api/v1/health || exit 1` (busybox `wget` ships in `alpine`, no extra package); `CMD ["node", "dist/main.js"]`.
   - No `ARG`/`ENV` ever holds a secret value; no `RUN prisma migrate deploy` anywhere in this file (that's an explicit deploy-time step, never baked into the image or run on boot).
   - Arch-neutral: no `--platform=` pin on any `FROM`, no apt/apk package that's arch-specific. Multi-arch (`arm64`+`amd64`) buildx/push is TASKS.md #43's job; this Dockerfile just has to build cleanly under either.
2. **`.dockerignore`** (new, **repo root** — matches the build context) — excludes `node_modules`, `**/node_modules`, `dist`, `**/dist`, `.git`, `coverage`, `**/coverage`, `.env`, `**/.env`, `!**/.env.example` (re-allow the example files), `*.log`, `.next`, `**/.next`. One root-level file so a future `apps/web/Dockerfile` (also root-context) reuses it — do not create a second one under `apps/api/`.

### Batch 4 — Prod compose + nginx (2 files, new)

1. **`infra/docker-compose.prod.yml`** (new) — prod overlay. `postgres`: `command: ["postgres", "-c", "shared_buffers=256MB"]` (deployment-plan §5's own tuning value), `restart: unless-stopped`, `volumes: [pgdata_prod:/var/lib/postgresql/data]`, `mem_limit: 320m`. `api`: `build: {context: ., dockerfile: apps/api/Dockerfile}`, `image: ${API_IMAGE:-ghcr.io/example/hub-api}:${IMAGE_TAG:-latest}`, `env_file: .env`, `restart: unless-stopped`, `depends_on: {postgres: {condition: service_healthy}}` (relies on base's `pg_isready` healthcheck), `networks: [hub-net]`, `volumes: [resources_data:/data/resources]`, `mem_limit: 180m` — **no `ports:` key** (internal only, reachable at `api:4000` on `hub-net`). `nginx`: `image: nginx:1.27-alpine`, `restart: unless-stopped`, `depends_on: [api]`, `environment: {APP_HOSTNAME: ${APP_HOSTNAME}}`, `ports: ["80:80", "443:443"]`, `volumes:` mounting `./infra/nginx/default.conf.template` → `/etc/nginx/templates/default.conf.template:ro` (nginx's official image auto-`envsubst`s anything under `/etc/nginx/templates/` into `/etc/nginx/conf.d/` at container start — no custom entrypoint script needed), `/etc/letsencrypt:/etc/letsencrypt:ro` (real certs land here on the VM later, out of scope), and `resources_data:/data/resources:ro`; `mem_limit: 32m`. Top-level `volumes: {pgdata_prod:, resources_data:}`.
2. **`infra/nginx/default.conf.template`** (new) — one `server{listen 80;}` block that 301-redirects to `https`; one `server{listen 443 ssl;}` block with `ssl_certificate`/`ssl_certificate_key` pointed at `/etc/letsencrypt/live/${APP_HOSTNAME}/{fullchain,privkey}.pem`, security headers (`Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`), `client_max_body_size 25m;`, two `limit_req_zone` directives (`login` 5r/m, `api` 30r/s) declared at the top of the file, a `location = /api/v1/auth/login` block applying the `login` zone (`burst=5 nodelay`) before proxying to `http://api:4000`, a `location /api/` block applying the `api` zone (`burst=10 nodelay`) proxying to the same upstream, a `location /files/ { internal; alias /data/resources/; }` block, and a `location / { return 503 "apps/web not built yet — see TASKS.md #40"; }` placeholder with a `# TODO(TASKS.md #40): proxy_pass http://web:3000;` comment directly above it. Both proxy blocks set `X-Forwarded-For $remote_addr` and `X-Forwarded-Proto $scheme` (matches `apps/api`'s existing `trust proxy` wiring in `main.ts`).

### Batch 5 — Deploy/smoke scripts + prod env template (3 files, new)

1. **`infra/scripts/deploy.sh`** (new, executable) — `set -euo pipefail`; requires `IMAGE_TAG` env var (fails loudly if unset); runs `docker compose -p hub-prod -f docker-compose.yml -f docker-compose.prod.yml --env-file .env` (relative paths — this script runs from `/opt/hub` on the VM, cwd, where CI has already staged both compose files) through, in order: `pull` → `run --rm api npx prisma migrate deploy` → `up -d` → invoke `infra/scripts/smoke.sh` (same directory as this script, resolved via `$(dirname "$0")`); on smoke failure, read a `.last_tag` file, `up -d` again with `IMAGE_TAG=$previous_tag` if one exists, and `exit 1`; on success, write the new tag into `.last_tag`.
2. **`infra/scripts/smoke.sh`** (new, executable) — `set -euo pipefail`; requires `APP_HOSTNAME`; polls `https://${APP_HOSTNAME}/api/v1/health` up to 10× (3s apart) for HTTP 200 via `curl -s -o /dev/null -w '%{http_code}'`, returns non-zero if it never comes back 200; includes a commented-out second check for the login page (`# TODO(TASKS.md #40): also check "https://${HOSTNAME}/"`) since `apps/web` doesn't exist yet to actually serve one.
3. **`infra/.env.prod.example`** (new) — every key `.env` on the VM must have, **all blank** (no real or placeholder-looking values, unlike the dev example): `APP_HOSTNAME`, `IMAGE_TAG`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `DATABASE_URL`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `SUPER_ADMIN_EMAIL`, `SUPER_ADMIN_PASSWORD`, `WEB_ORIGIN`, `COOKIE_SECURE=true` (only non-blank value — it's a fixed prod setting, not a secret), `B2_ACCOUNT_ID`, `B2_APPLICATION_KEY`, `B2_BUCKET`. Header comment states this is rendered onto the VM as `/opt/hub/.env` by the (not-yet-built, TASKS.md #43) deploy pipeline from GitHub Environment secrets — never committed with real values.

### Batch 6 — Extend Makefile with prod targets (1 file, edit)

1. **`Makefile`** (edit) — add a `COMPOSE_PROD` variable (`docker compose -p hub-prod -f infra/docker-compose.yml -f infra/docker-compose.prod.yml --env-file infra/.env.prod`) and targets `prod-build` (`$(COMPOSE_PROD) build`), `prod-up` (`$(COMPOSE_PROD) up -d`, with a comment that `infra/.env.prod` must be populated first — never committed), `prod-down`, `prod-logs`, `migrate` (`$(COMPOSE_PROD) run --rm api npx prisma migrate deploy` — the explicit, separate migration step), `smoke` (`bash infra/scripts/smoke.sh`). Extend the existing `.PHONY:` line to include all six new names.

## 6. Definition of Done gates

### Static gates (hub-reviewer — grep/pattern, exact)

- **S1 (no ports leak)**: `awk` per-service extraction of `infra/docker-compose.prod.yml` shows a `ports:` key **only** under the `nginx` service block — absent under `api` and `postgres`.
