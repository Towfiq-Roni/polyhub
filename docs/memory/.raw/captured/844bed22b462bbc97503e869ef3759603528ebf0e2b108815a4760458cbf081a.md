# ADR-0011: Derived Chart-of-Accounts reporting from the Transaction ledger

**Status:** Accepted
**Date:** 2026-09-08
**Source:** DEC-060, DEC-061, DEC-063, DEC-064; `docs/designs/REQ-33-derived-chart-of-accounts-reporting.md`

## Context

The stakeholder asked for Chart-of-Accounts-style financial reporting (trial balance,
profit & loss, balance sheet) after two same-day decisions had gone the other way:
DEC-061 removed `design/accounting.html`, a full double-entry bookkeeping *write-path*
module (Chart of Accounts + Journal Entries + Trial Balance, with manual entry) that
contradicted the spec's explicit "not an ERP: no double-entry accounting" non-goal, and
DEC-063 replaced a fake Chart-of-Accounts classifier in `payment-entry.html` with a flat
`TransactionCategory` tag. Business analysis on the stakeholder's follow-up request
confirmed the actual driver is internal preference for accrual-basis visibility — not an
external compliance, audit, or lender requirement that would force a real general ledger.

ADR-0005 (money as integer poisha) and ADR-0006 (immutable-ledger reversals) both assert
`Transaction`+`Account` (IN/OUT direction, computed balance) as hub's financial model,
with no account-type/chart-of-accounts concept. Given the confirmed internal-preference
driver, a second ledger system of record (a genuine `JournalEntry`/`JournalLine` write
path) would add dual-write consistency risk and rewrite most of Phase 0's 33 already-built
screens, for a need that doesn't require that weight.

## Decision

Add Chart-of-Accounts-style reporting (trial balance, P&L, balance sheet) as a **read-only
derived view** computed at query time from the existing `Transaction`, `Account`, and
`TransactionCategory` data — not a second ledger.

- **NEW `LedgerAccount`**: a small seeded reference table (14 rows: 1 Asset, 2 Revenue,
  8 Expense, 1 Equity plug, 2 Uncategorized fallbacks) classifying money movements for
  reporting purposes only. Distinct from the existing `Account` entity (Cash/Bank/MFS,
  a money-holding place) — no naming or conceptual overlap.
- **`TransactionCategory`** gains a nullable `ledgerAccountId` FK, type-compatibility
  validated server-side (an Income-direction category may only map to a Revenue-type
  `LedgerAccount`, Expense-direction to Expense-type) so the trial-balance identity can't
  be silently broken by a mismatched mapping.
- **No `JournalEntry`/`JournalLine` tables.** Trial balance and P&L are computed as
  `Equity_TB = Σ(Account.openingBalance) + cumulative(Income − Expense)`, which is always
  numerically identical to the summed cash balance by construction (every `Transaction`
  moves exactly one `Account` and exactly one `TransactionCategory` of matching
  direction) — the statements balance to zero without any stored plug or reconciliation
  step.
- **Balance Sheet uses a distinct formula**, `Equity_BS = Equity_TB + AR − AP`, folding in
  the existing Receivables/Payables computed reports as accrual Asset/Liability lines.
  Reusing `Equity_TB` directly (without the AR − AP adjustment) breaks
  Assets = Liabilities + Equity by exactly AR − AP — this was caught and fixed during
  `hub-solution-architect`'s design review (a real BLOCKER, not a style nit). Scoped to
  as-of-today only in v1; the Receivables/Payables engine has no as-of-a-past-date
  capability, so a historical Balance Sheet is deferred rather than shipped silently wrong.
- No new permission keys — reuses `reports.view`/`reports.export`, since this has no write
  path to gate differently from any other report.

Manual free-form journal-entry posting remains permanently out of scope — that is exactly
what DEC-061 correctly removed, and this decision does not reopen it. What changes is
narrower: hub's non-goal now reads "no *general-ledger write path*," not "no
Chart-of-Accounts *reporting* at all."

## Consequences

- ADR-0005 and ADR-0006 are **not modified** — their rationale (integer poisha, computed
  balance, immutable + reversal-only ledger, no second write path) is completely
  unaffected by this decision and remains the accurate description of hub's core
  financial model. This ADR adds a read-model on top, it does not amend the foundation.
- The `LedgerAccount` seed is static reference data in v1 (no admin CRUD) — a future
  request for user-editable chart-of-accounts structure, or for account hierarchy, is a
  new decision, not an extension of this one (the `parentId`/hierarchy idea was
  considered and explicitly dropped as speculative during design review — add it later
  only if a real requirement needs it).
- A historical point-in-time Balance Sheet is out of scope until the Receivables/Payables
  engine gains as-of-date capability — attempting one today would silently produce a
  Balance Sheet that doesn't balance, since cash/equity would reflect the requested past
  date while AR/AP would reflect today. Any future work enabling historical Balance
  Sheets must extend that engine first, not just remove the date restriction here.
- This is the first "derived report computed at query time over an immutable ledger plus
  a small seeded reference table" pattern in this codebase — flagged for a
  `workflow-blueprint` capture once built, so future accrual-style views clone this shape
  instead of reinventing it.
